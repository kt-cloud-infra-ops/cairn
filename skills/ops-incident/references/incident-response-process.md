# 사내 장애 대응 프로세스 (표준 예시) (장애 후속 대응 + 인시던트 사후 관리)

본 문서는 사내 장애 대응 가이드를 학습하여 정리한 reference. 운영 장애 발생 시 보고 절차/양식/사후 관리 표준이다.

- 학습 일자: 2026-05-21
- 적용 대상: 운영 장애 발생 시 보고/사후 관리 전 과정

## 1. 장애 대응 (복구 단계, 6~13단계 발췌)

| 단계 | 주체 | 행위 |
|------|------|------|
| 6 | 복구반 | 복구계획 수립 + 복구 수행 (상황반과 협의) |
| 7 | 복구반 | 복구 현황을 주기적으로 상황반과 공유 |
| 8 | 고객대응팀 | 고객 VOC 대응, VOC 누적 현황 주기 공유 |
| 9 | 관제팀 | 경과 공지 발송 + 등급 상향 등 경과시간 체크/공유 |
| 10 | 복구반 | VM 재기동 등 고객 서비스 영향 발생 시 **고객 공지 후 진행** |
| 11 | 복구반장 | 복구 완료 여부 판단 + 상황반 공유 |
| 12 | 관제팀 / 서비스운영팀 | 사내 장애 종료 / 고객 장애 종료 공지 |
| 13 | 상황반장 | 장애 대응 종료 |

## 2. 장애 후속 대응 프로세스

### 2.1 보고서 분리 원칙

| 대상 | 산출물 | 시행 조건 |
|------|--------|---------|
| 사내 | 사내 장애복구보고 | 필수 시행 |
| 사내 | 사내 장애 보고서 | 필요 시 |
| 고객 | 고객 장애 보고서 | 요청 시 |

### 2.2 장애등급 별 사내 보고 대상 및 방법

| 등급 | 장애 복구 보고 (보고대상 / 참조 / 방법) | 사내 장애 보고 (보고대상 / 참조 / 방법) |
|------|---------------------------------|---------------------------------|
| **1등급** | 대표이사 / 장애 전파대상과 동일 / Confluence & Slack | 대표이사 / 해당 운영담당, 사업담당, 유관부서 / Confluence & Slack |
| **2등급** | 본부장 / 동일 / 동일 | 본부장 / 동일 / 동일 *필요시 별도보고 |
| **3등급** | 본부장 / 동일 / 동일 | 본부장 / 동일 / - |
| **4등급** | 담당 / 동일 / 동일 | 담당 / 팀장 이상 / - |
| **관리장애** | 담당 / 담당 내 / Confluence | 담당 / 담당 내 / Confluence |
| **CNODE DOWN** | - / - / - | 담당 / 담당 내 / Confluence |

- 주1) 비 본부 체제 조직의 경우, 담당
- 주2) 보고 대상은 서비스 복구반(장애 주관 부서) 소속 담당. 본부장은 **필수 참조**
- ※ 2/3/4등급 사내 장애 보고는 필요에 따라 대표이사 별도 보고

### 2.3 장애 후속 대응 프로세스 흐름

```
[1] 장애 복구 보고          [2] 고객 장애 보고서       [3] (필요시) 사내 장애      [4] (필요시) 고객 장애
   (Confluence 등록)          작성 (PDF, Confluence)      보고서 작성                 보고서 업데이트
        │                          │                       (Confluence 등록)           (PDF, Confluence)
        │                          │                            │                          │
        ▼ SLACK 전파              ▼ 서비스운영팀/채널부서      ▼ 필요시 사내            ▼ 일반고객/주요기관
   기술본부/운영본부            제공 → 일반고객/주요기관      장애 보고                  제공
   사내 유관부서                  제공
```

## 3. 상세 프로세스

### 3.1 장애 복구 보고 (장애 종료 후 **3시간 이내**)

- 주체: 복구반장 (운영팀 또는 관리부서)
- 채널: Confluence & Slack
- 내용: 장애 대응에 대한 간략한 현황

| 구분 | 보고 항목 | 비고 |
|------|---------|------|
| 장애 정보 | 장애 대상, 장애 등급, 장애 일시 | - |
| 장애 영향도 | VOC 건수 | 고객서비스팀 제공 |
| 장애 영향도 | 서비스 영향 (장애 VM 규모) | - |
| 장애 내용 | 장애 내용 | - |
| 조치 내역 | 시간대별 조치 내역 | 관제팀 제공 |

**예외**: 이중화 환경에서 HA 등 정상 절체 메커니즘에 따라 서비스가 통상적인 절체 시간 내에 전환된 경우 **장애로 적용하지 않음**.

### 3.2 사내 장애 보고서 (장애 복구 후 **EPC 2영업일 / IPC 5영업일 이내** — 조직의 SLA 기준으로 교체)

- 주체: 복구반장
- 채널: Confluence

| 구분 | 보고 항목 | 비고 |
|------|---------|------|
| 장애 정보 | 장애 대상, 장애 등급, 장애 일시 | - |
| 장애 영향도 | VOC 건수 | 서비스운영팀 제공 |
| 장애 영향도 | 서비스 영향 (장애 VM 세부내역) | 세부 내역은 별첨 |
| 장애 내용 | 장애 내용 | - |
| 조치 내역 | 시간대별 조치 내역 | 관제팀 제공 |
| **장애 원인** | 장애 세부 원인 및 증빙 | **로그 등 증빙** |
| **개선 방안** | 개선 방안 및 이행 계획 | - |

### 3.3 고객 장애 보고서 (장애 복구 후 **EPC 2영업일 / IPC 5영업일 이내** — 조직의 SLA 기준으로 교체)

- 주체: 복구반장
- 작성 기준: 사내 장애 보고서 기반 + 필요 시 상황반 추가 협의
- 내용: 장애 계정, VOC 접수, VM별 가용율 등 **장애 고객에 국한된 내용**

| 구분 | 보고 항목 | 비고 |
|------|---------|------|
| 장애 정보 | 장애 대상 (고객 기준), 장애 일시 | - |
| 장애 정보 | 가용율 (필요시) | VM별 장애 시간 별첨 포함 |
| 장애 영향도 | 서비스 영향 (장애 VM 세부내역) | 세부 내역은 별첨 |
| 장애 내용 | 장애 내용 | - |
| 장애 원인 | 장애 원인 | - |
| 조치 내역 | 조치 내용 + 시간대별 조치 내역 | **VOC 접수 포함** |
| 개선 방안 | 재발 방지 대책 및 후속 계획 | - |

- 고객/주요기관이 보완 요청 시 **추가 보완하여 제공**

## 4. 인시던트 사후 관리

### 4.1 정기 인시던트 실무자 리뷰

- **주관**: 관제팀
- **주기**: 격주 (주기는 조직 기준으로 설정)
- **참석**: 해당 인시던트 관련 담당자 및 팀장
- **대상**: 정기 주기 내 발생한 모든 서비스의 인시던트
- **선정 기준**: 장애 / 미탐지 / 원인 분석이 필요한 건 / 특이사항 공유 필요 인시던트
- **예외**: 단순 반복성 인시던트는 리뷰 대상에서 제외
- **사후 관리**: 리뷰 결과 후속 관리 필요 사항은 **Action Item**으로 관리, 조치 완료 시까지 이행 현황 지속 추적·관리

### 4.2 월간 인시던트 리뷰

- **주관**: 관제팀
- **주기**: 매월 1회
- **참석**: 운영담당 및 팀장
- **목적**: 실무자 인시던트 리뷰 내역 / 미탐지 발생 내역 / 주요 개선 사항 / Action Item 진행 현황 종합 점검
- **사후 관리**: 주요 개선 사항 및 재발 방지 필요 사항은 Action Item으로 관리, 조치 완료 시까지 이행 현황 추적·관리

### 4.3 장애 리뷰 (Post-mortem)

**리뷰 대상** (종합 고려 — 서비스 영향도 / 장애 원인 / 재발 가능성 / 운영상 중요도):

- 고객 서비스에 영향이 발생한 장애
- 동일 또는 유사 장애의 재발 가능성이 있는 장애
- 원인 분석, 대응 적정성, 재발 방지 대책이 필요하다고 판단되는 장애
- 장애 대응 과정에서의 전파, 보고, 협업 등의 절차상 보완이 필요한 장애
- 그 밖에 조직 차원의 공유 및 관리가 필요하다고 판단되는 주요 장애

**제외 가능**: 단순·경미 장애로서 원인과 조치가 명확하고 재발 가능성이 낮은 경우

**리뷰 항목**:
- 장애 발생 원인
- 조치 경과
- 영향 범위
- 재발 방지 대책

**사후 관리**: 후속 관리 필요 사항은 Action Item으로 관리, 조치 완료 시까지 이행 현황 추적·관리

## 5. 특정 사고 적용 가이드 (예시 섹션)

> 이 섹션은 특정 사고 적용 예시였습니다. 실제 사고 발생 시 해당 내용으로 교체하여 사용하세요.

| 항목 | 판정 |
|------|------|
| 장애 등급 | `[미확인]` — 사용자 확인 필요 |
| 보고 대상 | 담당 → 팀장 이상 (관리장애면 담당 내) |
| 보고 채널 | Confluence 또는 Confluence & Slack (등급에 따라) |
| 장애 복구 보고 기한 | 장애 종료 후 **3시간 이내** |
| 사내 장애 보고서 기한 | **EPC 2영업일 / IPC 5영업일 이내** (조직의 SLA 기준으로 교체) |
| 고객 장애 보고서 | `[미확인]` — 고객 영향 여부에 따라 결정 |
| 장애 리뷰 대상 여부 | `[미확인]` — 재발 가능성/원인 분석 필요 여부로 판단 |

### 5.1 단계별 적용 체크리스트

- [ ] 장애 복구 보고 (3시간 이내): Confluence + Slack 등록
- [ ] 사내 장애 보고서 작성 필수 항목: 장애 정보 / 영향도 / 내용 / 조치 내역 / **장애 원인 + 증빙** / **개선 방안 + 이행 계획**
- [ ] 장애 리뷰 (Post-mortem): 사후 진행, Action Item 도출
