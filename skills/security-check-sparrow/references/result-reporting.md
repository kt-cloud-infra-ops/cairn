# 결과 집계와 보고

## 1. 집계값을 단독으로 신뢰하지 않는 이유 (CRITICAL)

클라이언트 출력에서 등급·건수를 읽는 정규식이 체커명을 `[A-Z_]+` 로 잡으면, 점이 포함된 체커명(예: `.KOTLIN`)이
매칭되지 않아 **해당 건수가 통째로 빠진다.** 원본 래퍼에 이 오집계가 있었다.

번들 래퍼 `skills/security-check-sparrow/scripts/run_sparrow.sh` 는 패턴을 `[A-Za-z0-9_.]+` 로 고쳐 이 누락을 해소했다.
(검증: `.KOTLIN 3건` + `OTHER_CHK 5건` 입력 → 이식본 8건 / 원본 5건)

그래도 **텍스트 파싱은 보조 지표**다. 출력 포맷이 바뀌면 다시 틀어질 수 있으므로 확정 건수는 항상 REST로 재확인한다.

> `Total Risk Sum: 0` 출력 하나로 "결함 없음"을 보고하지 않는다.

## 2. REST 재확인

로그인 쿠키를 사용해 조회한다.

```text
GET /api/1/scans/<scan-id>/info      # 스캔 메타데이터
GET /api/1/scans/<scan-id>/issues    # 실제 결함 목록
```

- `scan-id`는 클라이언트 출력 또는 콘솔 URL에서 얻는다
- 등급별 건수를 여기서 다시 세어 보고한다
- REST 조회가 불가하면 "집계 미확인"으로 표기하고 `통과`로 보고하지 않는다

## 3. 위험 등급

| 등급 | 의미 |
|------|------|
| 1 | 최고 위험 |
| 2~4 | 중간 위험 구간 |
| 5 | 정보성 — 총합에서 제외 (래퍼도 1~4만 합산) |

등급 체계가 조직 룰셋에 따라 다르면 실제 콘솔 표기를 따르고, 보고에 기준을 명시한다.

## 4. 보고 형식

```markdown
## Sparrow SAST 결과 — <저장소명>

- 프로젝트 키: <자식 키>
- 스캔 ID: <scan-id>
- 분석 레벨: <level>
- 집계 기준: REST /api/1/scans/<id>/issues

| 위험 등급 | 체커 | 결함 수 |
|-----------|------|---------|
| 1 | ... | N |
| 2 | ... | N |

- **총 결함(1~4등급)**: N건
- 결과 콘솔: <서버>/scans/<id>/info , <서버>/scans/<id>/issues
```

규칙:

- 자격증명·계정 정보를 포함하지 않는다
- 실패·중단된 대상은 성공 대상과 **분리해서** 표기한다
- 일부만 성공한 경우 "전체 통과"라고 쓰지 않는다
- 결함 상세(코드 스니펫 포함)는 내부 보고에만 쓰고 외부로 전송하지 않는다
