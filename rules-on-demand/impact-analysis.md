# Cross-Cutting Impact Analysis

## 핵심 원칙 (CRITICAL)

새 엔티티/테이블/기능을 기존 시스템에 추가할 때, **기능 개발 외에 기존 코드/쿼리/데이터에 파급되는 항목을 반드시 검토**한다.

## 언제 수행하는가

아래 상황에서 자동으로 영향도 분석을 수행:

1. **새 테이블 추가** — 기존 쿼리가 JOIN하던 테이블에 UNION이 필요한지
2. **새 코드값/타입 추가** — 공통코드, 매핑 테이블에 등록이 필요한지
3. **기존 스키마 변경** — ALTER TABLE 시 기존 INSERT/SELECT 영향
4. **새 도메인 엔티티** — 권한체계, 검색조건, 엑셀 다운로드, 대시보드 통계 등 횡단 기능

## 검토 체크리스트

| # | 항목 | 확인 |
|---|------|------|
| 1 | 기존 쿼리 JOIN 패턴 — 새 데이터가 기존 조회에서 누락되지 않는가 |  |
| 2 | 공통코드/매핑 테이블 — 새 타입/값이 등록되어 있는가 |  |
| 3 | 권한 체계 — 새 데이터가 기존 권한 필터에 포함되는가 |  |
| 4 | 검색/필터 조건 — 드롭다운, 필터에 새 항목이 나오는가 |  |
| 5 | 엑셀/리포트 — 다운로드 쿼리에 새 데이터가 포함되는가 |  |
| 6 | 대시보드/통계 — 집계 쿼리에 새 데이터가 반영되는가 |  |
| 7 | 기존 데이터 마이그레이션 — 새 컬럼의 기존 row 기본값 |  |
| 8 | 배치/스케줄러 — 백그라운드 작업에서 새 데이터 처리 |  |

## 풀스택 레이어 체크리스트 (CRITICAL)

기능 개발 시 **모든 레이어를 빠짐없이 점검**한다. 레이어 하나라도 누락하면 프로덕션에서 장애 발생.

| # | 레이어 | 확인 항목 | 확인 |
|---|--------|----------|------|
| 1 | **DDL/스키마** | 테이블/컬럼 생성, 인덱스, 제약조건, 마이그레이션 스크립트 |  |
| 2 | **데이터 접근** | ORM/Mapper/쿼리 — CRUD 전체, 조인 패턴, 페이지네이션 |  |
| 3 | **비즈니스 로직** | 서비스 레이어 — 트랜잭션, 유효성 검증, 에러 처리, 로깅 |  |
| 4 | **API/엔드포인트** | 라우팅, 인증/인가, 요청/응답 스키마, 에러 응답 |  |
| 5 | **스케줄러/배치** | 주기 작업, 타임아웃, 재시도, 실패 알림 |  |
| 6 | **UI** | 화면, 폼, 테이블, 필터, 에러 표시, 접근성 |  |
| 7 | **메시징/연동** | 외부 시스템 호출, 이벤트 발행/구독, 알림 채널 |  |
| 8 | **설정/인프라** | 환경변수, 설정 파일, 배포 스크립트, 프로시저 등록 |  |

> 기능 하나를 구현할 때 위 8개 레이어 중 해당하는 것을 모두 체크한다.
> "해당 없음"도 명시적으로 판단한다 (암묵적 생략 금지).

## Spec-First 외부 연동 (CRITICAL)

외부 API/시스템과 연동할 때 **실제 스펙을 먼저 확인**한 후 구현한다.

1. **API 스펙 확인**: Swagger/OpenAPI 문서 또는 실제 응답 JSON 샘플 확보
2. **인증 방식 확인**: Bearer, API Key, Basic, OAuth 등 — 추정 금지
3. **페이지네이션/에러 구조 확인**: 실제 응답 구조 기준으로 파싱 로직 작성
4. **연동 테스트**: 로컬 또는 스테이징 환경에서 실제 호출 검증

**금지**: 기존 코드 패턴이나 일반적 관행으로 API 스펙을 유추하여 구현

## Cross-layer 데이터 흐름 추적 (CRITICAL)

단일 데이터가 레이어를 횡단하며 변형/손실/무시되는 지점을 추적한다.

### 추적 파이프라인

```
SQL(값 생성) → Mapper(전달) → Service(DTO 변환) → Controller(응답) → JSP/API(출력)
```

### 필수 체크 항목

| # | 체크 | 설명 |
|---|------|------|
| 1 | UNION ALL 상수 컬럼 | 빈 문자열 `''`, null, 하드코딩 상수가 최종 출력(UI/API/메시지)에 노출되는지 |
| 2 | 빈 문자열 vs null 구분 (SQL) | `nvl()`, `COALESCE()`가 빈 문자열(`''`)도 처리하는지 확인 |
| 2b | 빈 문자열 vs null 구분 (App) | `StringUtils.defaultIfEmpty()`, `Optional.orElse()` 등이 빈 문자열을 통과시키는지 확인 |
| 3 | Mapper → DTO 매핑 | resultMap/resultType에서 컬럼 누락, 타입 불일치, alias 오류 |
| 4 | Service 변환 | DTO → 출력 포맷 변환 시 값 손실 (null 체크만 하고 빈 문자열 통과) |
| 5 | 출력단 렌더링 | JSP/API 응답에서 빈 문자열이 "빈 칸"으로 보이는지, 아예 안 보이는지 |

### 트리거 조건

아래 패턴 발견 시 반드시 데이터 흐름 추적 수행:
- UNION ALL에서 `''` 또는 `NULL AS 컬럼명` 패딩
- 기존 쿼리에 새 테이블/뷰 JOIN 추가
- Mapper resultMap에 새 컬럼 추가
- Builder/Formatter 클래스에서 조건 분기 변경

## 로컬 검증 워크플로우

개발 완료 선언 전 **로컬 환경에서 실제 동작을 검증**한다.

| 단계 | 내용 |
|------|------|
| 1. DB 검증 | 로컬/개발 DB에서 DDL 실행, 쿼리 결과 확인 |
| 2. 단위 동작 | 비즈니스 로직 단위 테스트 또는 수동 검증 |
| 3. API 검증 | 엔드포인트 호출하여 요청/응답 확인 |
| 4. UI 검증 | 화면에서 CRUD 전체 흐름 확인 |
| 5. 외부 연동 | Mock 서버 또는 스테이징으로 연동 테스트 |

외부 API를 로컬에서 호출할 수 없는 경우: Mock 서버(WireMock, json-server 등)로 실제 응답 구조를 재현하여 테스트.

## 산출물

영향도 분석 결과는 **프로젝트 레포 `docs/features/` 내 설계 문서의 별도 섹션**(예: "기존 쿼리 영향도 분석")으로 포함한다. 임시 문서(temp/)가 아닌 프로젝트 레포 설계 문서에 포함하여 추적 가능하게 한다.

> **하네스 적용 시**: cross-cutting 8항목은 CPS(`## 영향도 분석`)에 1차 기록하고, 설계 상세는 PRD(`## 풀스택 레이어 설계`)/Architecture에 확장한다. → `agents/skills/harness-dev-process/`

## 교훈 (테이블 추가 사례)

- 신규 테이블(`<YOUR_TABLE>`) 추가 시, 기존 테이블을 JOIN하는 쿼리를 30+ 건 수정해야 할 수 있음
- 공통코드, 구역 매핑, 권한그룹, 엑셀, 대시보드 등 8개 이상의 횡단 항목이 연쇄 영향받음
- 기능 설계서에 이 내용이 빠져 있어 사후에 cross-cutting 점검 티켓 추가 생성
- AI 코드 생성 vs 개발사 비교에서 확인된 갭: 풀스택 레이어 누락, 외부 API 스펙 유추, 로컬 검증 미수행

## 교훈 (연관 테이블 누락 사례)

- 메인 테이블(`<YOUR_TABLE>`) DB 직접 SQL 작업 시 연관 서브 테이블(`<YOUR_TABLE>_sub`) 처리를 누락해도 DB 오류 없이 통과 (제약 없음)
- 판단 기준이 애플리케이션 코드에만 존재하여 비가시적 — DB만 보면 놓침
- **DB 직접 작업 요청이 와도 반드시 도메인 서브에이전트와 사전 확인**
- 팀별 도메인 규칙: `agents/knowledge/lessons/db/<YOUR_SERVICE>-<YOUR_TABLE>-rules.md`
